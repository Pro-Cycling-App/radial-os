# Radial Gatekeeper

Read-only access to the Radial production database for agents and gadgets, deployed as
`radial-os-gatekeeper` and bound as `GATEKEEPER_CUSTOM` (the starter's custom-gatekeeper slot).
Auto-provisioned: no OAuth, no per-user credential — every signed-in user gets the same
`RadialSession` singleton, and every read is recorded as an observation.

## The API

`src/types.d.ts` is the contract; `src/types-code.ts` is its agent-facing copy, regenerated by
`pnpm run types:code` (edit `types.d.ts`, never the copy).

| Method | What it does |
| --- | --- |
| `query(sql, params?)` | Runs one read-only statement. Positional `$1…` params. Results return in full; a result above 4 MB of JSON is rejected, so `LIMIT`. |
| `listTables()` | Tables and views in `public`. |
| `describeTable(name)` | Columns of one table or view. |
| `getDeploymentInfo()` | The operator text from `deployment.jsonc` (`customGatekeeper.name` / `.message`). |

## Why it is safe to hand out

The fence is the database role, not this code. `DATABASE_URL` connects as **`radial_os`**: `SELECT`
on the public schema (default privileges cover new tables), nothing else; a role-level
`statement_timeout` of 15 s; and the connection string points at the **read-only pooler**, which
rejects writes at the endpoint itself. The monorepo's ADR 2026-021 is the role model; the
credential lives in the monorepo's `sec os` unit (`RADIAL_OS_DATABASE_PASSWORD`) and the URL is
composed from it at install time — see `docs/os/README.md` there.

`radial-db.ts` adds two caller-side guards on top: a deny-list of primitives that reach outside
the database even for a `SELECT`-only role (`dblink`, `http_*`, `pg_read_file`, `COPY … PROGRAM`),
and the result-size cap.

## Observer policy

`CustomVerifier.verify()` admits every observer. Cloudflare Access already limits sign-in to the
team, and the data behind this gatekeeper is the same read-only set for everyone on it, so a shared
gadget shows a collaborator nothing they could not query themselves. Revisit if the role ever gains
access to per-person data.

## Class names

`CustomGatekeeper`, `CustomAccount`, `CustomVerifier`, `CustomSessionImpl` keep the starter's names
on purpose. The Workshop stores stubs to the account and the singleton class irrevocably, so a
rename would orphan every existing connection. Only descriptions, the session type and the binding
name say Radial.

## Check

```sh
pnpm run test:run
pnpm run types:check
pnpm exec wrangler deploy --dry-run
```

Secrets: `DATABASE_URL` is declared required in `wrangler.jsonc`; install it with
`wrangler secret put DATABASE_URL --name radial-os-gatekeeper` (the monorepo doc has the composed
one-liner). Never put it in `wrangler.jsonc` or `deployment.jsonc`.
